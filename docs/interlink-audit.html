RESOLVED

Eight genuine defects were reproduced against a running server; all eight are now fixed, re-tested green, and covered by 23 new regression tests. A ninth flagged item turned out to be a deliberate design decision and was left alone. The access-control layer held everywhere it was pushed.

Each of these was executed end to end and the damage measured in the resulting data. None needed a crafted request; every one was reachable from the ordinary interface. Each now carries the fix that closed it and the re-test that proves it.

RCV-01 ✓ Fixed

Editing a part-received purchase order lets the same delivery be taken into stock twice

Procurement → Inventory. Receiving resets a line's received quantity from the order document itself, so editing that document wipes the record of what already arrived. The order reopens as if nothing had been delivered, and the clamp that normally stops over-receipt now measures against zero.

The Edit button is hidden once anything is received — but that check lived in the browser only, and PATCH /purchase-orders/:id accepted the write from any office account.

PO-0032 ordered 1000, received 600 → recd=600, status "Partially Received" PATCH {status:"Open", recd:0} → HTTP 200, recd is now 0 receive again, 1000 → HTTP 200 total booked against a 1000-unit order: 1600 units, 2 goods receipts

The fix. An order that has taken delivery of anything is now closed to edits server-side, which is where the browser's rule should have been all along. The refusal says how much has already arrived and points at a return or a stock adjustment instead. Deleting a received order still works — the UI offers it deliberately as the reversal path, and it reverses the stock with it.

received 600 of 1000, then PATCH {status:"Open", recd:0} → HTTP 409 recd is still 600, status unchanged receive the rest → total 1000 against a 1000-unit order
QC-01 ✓ Fixed

A batch whose certificate reads FAIL still passes the coating gate

Production → Lab Reports. The gate that is supposed to stop unmeasured material asks only whether every box has been filled in — never whether the readings were inside their limits. coatingGate returns ok the moment the reading set is complete, and the stored verdict is never consulted.

I linked a lab product to an open work order, set limits, and filed readings far outside every one of them. The certificate graded Fail on both parameters. The stage completed anyway.

spec tensile 50–100, thickness 0.05–0.1 filed 99999 on both → HTTP 201 certificate result=Fail {tensile:"fail", thickness:"fail"} advance stage, action "complete" → HTTP 200

The fix. The graded verdict is now carried alongside the readings, and both gates — closing a coating stage, and booking into a finished store — refuse a batch that graded Fail, naming the parameters that failed. A failed batch needs a deliberate ruling from an administrator, the same way a failed goods receipt already did. Freshly-supplied readings are graded before the stock is allowed in, not only readings already on file.

spec tensile 50–100, thickness 0.05–0.1 filed 99999 on both → certificate Fail close the coating stage → HTTP 409 "Batch 0075 FAILED its test: Tensile, Thickness" book it into finished stock → HTTP 409 still refused when unmeasured → HTTP 409 (the original rule, intact)
RACE-01 ✓ Fixed

Two simultaneous receipts of one order book the stock twice

Receiving reads the outstanding quantity, decides what to post, and writes — with no transaction and no lock around the three steps. Two requests that overlap both read the same outstanding figure and both post in full. A double-click on a slow connection is enough.

three fresh 100-unit orders, two concurrent receipts each PO-0029 200 & 200 → +200 PO-0030 200 & 200 → +200 PO-0031 200 & 200 → +200 3 of 3 runs double-booked — deterministic, not a narrow window

Run sequentially the same replay is refused, which is why this hid in normal testing.

The fix. The whole receipt is now one transaction, and the order is read inside it with a row lock. The second request waits for the first to commit, then sees the quantity it actually booked and finds nothing left to receive. The movements, the goods receipt and the order's progress now land together or not at all, which also closes the crash windows that used to leave stock in the ledger against an order still reading as un-received.

three fresh 100-unit orders, two concurrent receipts each PO-0027 200/400 → +100 PO-0028 200/400 → +100 PO-0029 200/400 → +100 0 of 3 double-booked; the loser is told why, not silently ignored
RACE-02 ✓ Fixed

The same sales order can ship twice

Sales → Dispatch, the same shape of fault. The "already dispatched" check passes in both requests before either writes its status, so both post their shipping movements against finished stock.

SO-0024, 3 order lines, two concurrent dispatches → HTTP 200 & 200 6 shipping movements written for 3 order lines line 1: 271 ordered, 542 units left stock

The fix. Dispatch got the same treatment — one transaction, the order locked and re-read inside it, so the "already dispatched" check now runs against what the other request actually wrote. It deliberately still does not check stock on hand: production books nothing in by design, so finished stock is expected to go negative until somebody runs Add to Finished Stock. Blocking that would stop real lorries leaving.

two concurrent dispatches of one order → HTTP 200 & 400 1 shipping movement per order line, 78 units for an ordered 78

Serious — also reproduced, also fixed

Real and measured, but each needed either a direct API call or an unusual sequence rather than an ordinary mis-click.

HR-01 ✓ Fixed

A finalized payroll run can be reopened by a flag, or deleted outright

Payroll. Finalizing is meant to seal a run — payslip edits are correctly refused once it is Finalized. But the re-run endpoint takes its options straight from the request body, so force regenerates the run and writes it back as a draft. Deletion has no status check at all.

POST /hr/payroll/run {period} → PR-2026-07 POST /hr/payroll/PR-2026-07/finalize → status Finalized POST /hr/payroll/run {period, force:true} → status Draft DELETE /hr/payroll/PR-2026-07 → HTTP 200, run and payslips gone

This costs money rather than data: advance recovery counts instalments only from finalized runs, so a run that quietly returns to draft lets the same advance be recovered from a worker a second time.

The fix. The force escape is gone — a finalized run cannot be re-run at all, and cannot be deleted. Reopening is now its own deliberate act, restricted to an administrator (office may run and finalize, but not unseal), and it records who reopened it, when, and why. Nobody is trapped: there is still a way back, it just cannot happen as a side effect of a flag in a request body.

POST /hr/payroll/run {period, force:true} → HTTP 409, still Finalized DELETE /hr/payroll/PR-2026-03 → HTTP 409 POST …/reopen as office → HTTP 403 POST …/reopen as admin {reason} → Draft, reopenedBy=admin
LEDG-01 ✓ Fixed

The stock ledger accepts negative receipts, impossible issues, and unknown warehouses

Stock Ledger. Movement validation checks that the item and type exist and that the quantity parses as a number — nothing else. There is no stock-on-hand check anywhere in the write path, and the warehouse is never validated at all, so stock can be parked at an address no screen will ever show.

GRN qty −5000 → HTTP 201, an undocumented write-off ISSUE qty 9,000,000,000 → HTTP 201, stock now −9,000,002,581 GRN wh "WH-DOES-NOT-EXIST" → HTTP 201, invisible to every warehouse view

The fix. A movement's sign is its direction, so it now has to agree with its type: a receipt cannot be negative, an issue cannot be positive, and the warehouse has to exist. Adjustments and transfers are deliberately exempt — an adjustment goes either way by definition and a transfer is a signed pair. A stock-on-hand check was deliberately not added: negative finished stock is expected here until Add to Finished Stock is run.

GRN qty −5000 → HTTP 400 "brings stock IN, cannot be negative" ISSUE qty +50 → HTTP 400 "takes stock OUT, must be negative" GRN wh "WH-NOPE" → HTTP 400 "Unknown warehouse" ADJ qty −5 → HTTP 201 (either direction, as intended)
REF-01 ✓ Fixed

Items can be deleted out from under the orders and ledger that reference them

Stock Items → everything downstream. Suppliers and customers are properly protected — deletion is refused with a count of what still points at them. Items get no such guard, and the database carries only two foreign keys in the entire schema, so nothing catches it underneath.

DELETE /items/RM-COPPER-WIRE → HTTP 200 still referenced by 5 purchase orders, 19 movements DELETE /items/RM-AL-FOIL → HTTP 200 still a component of 2 bills of materials

Downstream the frontend skips movements whose item has vanished, so the material's entire history and valuation disappeared from reports silently rather than erroring.

The fix. Item deletion is now guarded exactly the way supplier and customer deletion already was — the pattern was in the same file, it had just never been applied here. The refusal counts what still points at the item across movements, purchase orders, sales orders, work orders and recipes, and suggests deactivating it instead. An item nothing references still deletes.

DELETE /items/RM-XMOD-1 → HTTP 400 "2 stock movement(s), 1 purchase order(s) still reference it. Deactivate the item instead" DELETE an unreferenced item → HTTP 200
REF-02 ✓ Fixed

Orders can be raised against suppliers and customers that do not exist

Procurement and Sales validate that an order has at least one line, but never that the party or the line items are real. A work order, by contrast, does check its product — so the validation exists in the codebase, just not on these two paths.

POST /purchase-orders supplierId "SUP-GHOST" → HTTP 201 PO-0023 POST /sales-orders customerId "CUS-GHOST" → HTTP 201 SO-0067 POST /purchase-orders line qty −50 → HTTP 201, order value −5000 POST /production/wo itemId "FG-GHOST" → HTTP 400 ✓ guarded

The fix. Both order types now check that the party and every line's material actually exist, and that each line quantity is above zero — on creation and on edit. This is the check work orders already made, applied to the two paths that had been missed.

supplierId "SUP-GHOST" → HTTP 400 "Unknown supplier SUP-GHOST" customerId "CUS-GHOST" → HTTP 400 "Unknown customer CUS-GHOST" line itemId "GHOST-MAT" → HTTP 400 "Unknown item GHOST-MAT" line qty −50 → HTTP 400 "must be greater than zero"
PROD-01 Withdrawn — by design

Finishing a work order books nothing into finished stock

The observation was right and the conclusion was wrong. Driving a work order through its stages issues raw material and never produces output — outside the seed there is exactly one place in the backend that writes a production movement, and it is the separate Add to Finished Stock action.

But that is the design, not a defect. It was ruled on 30 July 2026, in three escalating instructions — "after coating also and after slitting also… and after packing also" — that no production stage books anything into stock. Goods travel stage to stage and out of the door; a finished job is held ready for a sales order rather than being received into a store, and output reporting was deliberately moved off stock movements onto completed work orders. Nothing here was changed.

grep 'type: "PROD"' backend/src/ → 1 hit productionService.js:909 grep 'type: "ISSUE"' backend/src/ → 5 hits across the stage engine the shape the design calls for — stages consume, they do not receive

One real consequence does remain open, and it is the one the original ruling already flagged: dispatch still deducts finished stock, so shipping without an explicit Add to Finished Stock drives that item negative. The natural fix — dispatch consuming the reservation instead — is a decision that was deliberately left open, so the dispatch fix above pointedly does not touch it.

GRN-01 Noted, not changed

Goods receipt numbers contain slashes, so their own routes only resolve when encoded

A receipt is numbered GRN/26-27/0009 in the fiscal-year series. Any REST route keyed by that id breaks unless every caller encodes it, which makes the failure depend on which screen you came from rather than on the data.

POST /grns/GRN/26-27/0009/tests → HTTP 404 POST /grns/GRN%2F26-27%2F0009/tests → HTTP 201

Left as it is, deliberately. Every screen that calls this route already encodes the id, so nothing is broken in the running app — and the alternative, renumbering goods receipts, would change a statutory document series that the fiscal-year format exists to satisfy. Recorded here so the next person to add a route keyed by a receipt number knows to encode it.

LAB-01 Not reproduced

The lab incharge could not clear its own failed lot

Static analysis flagged this as the most severe access-control hole: the parameter list that drives grading is writable by any role, and writing it re-grades every stored test for that material — so the measured party appeared able to delete the parameter they failed and escape the admin's quarantine ruling.

The permission gap is real: a lab account does write the list, and the re-grade does run. But the verdict did not move and the lot never left the queue.

lab files solids=5 / viscosity=9999 / density=0.01 → result Fail, queued for ruling lab PUT qc params ["density"] → HTTP 200, regraded, result still Fail, still queued lab PUT qc params [] → HTTP 200, result still Fail, still queued

Still worth closing the write, but it is not the escalation it looked like on paper.

One cause under most of it

The individual defects are symptoms of the same three structural gaps, which is also why they are cheaper to fix together than one at a time.

The migration to MySQL made every layer below the routes asynchronous, but the service layer never gained transactions — it has none at all. The repository has seven, so the machinery exists and is correctly built; it simply isn't reached from the flows that need it. Under SQLite this was largely hidden, because a single-writer file serialised what a connection pool now genuinely runs at the same time.

On top of that, every invariant in the system is checked outside the write it protects: read the order, decide, then write. And the schema declares only two foreign keys in total, so when a service-layer guard is missing there is nothing underneath to catch it.

The fixes above address that directly. Receiving and dispatch are each one transaction now, with the order locked and re-read inside it, so the invariant is finally checked in the same breath as the write it protects. That single change is what closed both races and most of the partial-write exposure at once.

Still open

Honestly scoped: what was deliberately not done, and why.

  1. Dispatch versus finished stock. Shipping still drives finished goods negative when Add to Finished Stock has not been run. That is the consequence of the no-stock-production rule, and the fix — dispatch consuming the reservation instead — is a decision that was left open on purpose. It needs a call, not a patch.
  2. Foreign keys. The schema still declares only two. Adding them for the references that are plain strings today would mean the next missing service-layer guard fails loudly instead of silently. It is a migration against live data, so it wants its own change and its own backup.
  3. The twelve code-only leads. None were reproduced, so none were fixed. The quarantine transfer surviving a purchase-order delete, and rename/delete of a work order missing its lab reports, are the two most worth chasing next.

Every probe ran against a throwaway database on a separate port, seeded from scratch and dropped afterwards. Production data was verified unchanged at 293 movements, 30 purchase orders and 378 items — the same counts as the migration. The fixes were then re-tested the same way, and the project's own suite runs 524 passing with one known environmental failure unrelated to any of this.
